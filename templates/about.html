Problem

Farmers and mechanics rely on memory, notebooks and glovebox receipts to remember when a tractor was last serviced or what was done to it. Records get lost, repairs get repeated, and nobody can say which machine is costing the most to keep running.

Solution

FarmFix stores equipment, repairs and service records in one relational SQLite3 database, so a machine's full history is a query rather than a search through a drawer. Because the costs are computed from the records every time a page loads, they can never drift out of date.

How SQLite3 is used

SQLite3 is an embedded database: the whole database is a single file on disk and the engine runs inside the application process. There is no server to install, no port, no username and no password. Flask opens it with sqlite3.connect("database/farmfix.db") once per request and immediately issues PRAGMA foreign_keys = ON, because SQLite ships with foreign-key enforcement switched off for backwards compatibility — and the setting lives on the connection, not in the file.

Nothing here is faked with localStorage, a JSON file, or a hosted database. Delete database/farmfix.db and the application has no data at all — it refuses to start and tells you to run python database/init_db.py.

Database relationships

  • Equipment 1 → 0..* Repair — repairs.equipment_id is a NOT NULL foreign key, ON DELETE CASCADE. A repair cannot exist without the machine it was done on.
  • Equipment 1 → 0..* Maintenance — maintenance.equipment_id, same rule.
  • Mechanic 0..1 → 0..* Repair — repairs.mechanic_id is nullable, ON DELETE SET NULL. A repair the operator did in-house has no mechanic on record, and removing a mechanic must not delete the repairs they worked on.

Both core associations are one-to-many, so the foreign key goes on the "many" side and no junction table is needed — a junction table is the right answer to a many-to-many and the wrong answer to a one-to-many.

Important SQL queries

1. Equipment repair history — the JOIN the assignment asks for

SELECT equipment.name,
       repairs.repair_date,
       repairs.problem,
       repairs.cost
FROM equipment
JOIN repairs ON equipment.equipment_id = repairs.equipment_id
ORDER BY repairs.repair_date DESC;

2. Repair count and cost per machine — JOIN + GROUP BY + aggregates

SELECT e.name,
       COUNT(r.repair_id)       AS repairs,
       COALESCE(SUM(r.cost), 0) AS total,
       COALESCE(AVG(r.cost), 0) AS average,
       COALESCE(MAX(r.cost), 0) AS dearest
FROM equipment e
LEFT JOIN repairs r ON r.equipment_id = e.equipment_id
GROUP BY e.equipment_id, e.name
ORDER BY total DESC;

3. Lifetime cost per machine — two child tables, done safely

SELECT e.name,
       (SELECT COALESCE(SUM(r.cost),0) FROM repairs r
         WHERE r.equipment_id = e.equipment_id)
     + (SELECT COALESCE(SUM(m.cost),0) FROM maintenance m
         WHERE m.equipment_id = e.equipment_id) AS lifetime_cost
FROM equipment e
ORDER BY lifetime_cost DESC;

Correlated subqueries, not two LEFT JOINs. Joining both child tables in one query multiplies the rows — a machine with 3 repairs and 3 services produces 9 rows, and every SUM comes out three times too high. This is the bug written up in documentation/DEBUGGING.md.

4. HAVING — filtering groups instead of rows

SELECT e.name, COUNT(*) AS repairs, SUM(r.cost) AS total
FROM repairs r
JOIN equipment e ON e.equipment_id = r.equipment_id
GROUP BY e.equipment_id, e.name
HAVING COUNT(*) >= 2 AND SUM(r.cost) > 500
ORDER BY total DESC;

5. Recent activity across two tables — UNION ALL

SELECT 'Repair' AS kind, r.repair_date AS on_date, r.problem AS summary, r.cost
FROM repairs r
UNION ALL
SELECT 'Service', m.service_date, m.service_type, m.cost
FROM maintenance m
ORDER BY on_date DESC
LIMIT 8;

Every query in the app can be revealed in place with the “Show SQL” buttons on the Dashboard, Equipment, Equipment detail, Repairs, Maintenance, Mechanics and Reports pages.

AI-assisted learning

We used an AI assistant to learn SQLite3, then checked every answer against the real database instead of trusting it. Six interactions are documented in documentation/AI_LEARNING_EVIDENCE.md, including ones where the AI was wrong:

  • Foreign keys look enforced but are not until every connection runs PRAGMA foreign_keys = ON.
  • Two LEFT JOINs silently tripled our cost totals — valid SQL, wrong numbers, no error message.
  • An INNER JOIN hid the in-house repairs, because their mechanic_id is NULL.
